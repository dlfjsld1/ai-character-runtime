# 같은 OpenAI 키를 판단 모델에 쓰는 방안 — 2026-10-14

최신: [입력 해석 구조 v2 구현 결과](./INTERACTION_V2_RESULT.md). 이전21/24에 보류8·확인 질문1이 포함돼 참여 기준 재분석은12/24다. v2는 구현했지만 실제 새 호출은0이다. 아래 조사·v1 비교는 당시 기록이다.

후속 상태: 사용자 “써도됨” 승인 뒤 [고정 계획](./GOAL2_DECISION_COMPARISON_PLAN.md)대로 실제24회 실행했다. 같은 키의 endpoint 접근과 응답 계약은 확인했지만 기능21/24로 후보는 거절했다. 기존 OpenAI 총 USD1 원장을 공유했으며 알려진 판단 비용 USD0.0051805, 확인12·운영 교체·새 Stage0이다. [현재 결과](./GOAL2_DECISIONS_RESULT.md)가 우선한다. 아래는 실제 실행 전의 조사 기록이다.

결론: 후보로 검토할 가치가 있다. 우선 생성 품질을 확정하고, 판단은 Jev와 비교한 뒤 교체 여부를 정한다. 모든 입력에 Jev와 OpenAI 판단을 둘 다 붙이는 방식은 기본안으로 권하지 않는다. 이번에는 조사만 했으며 Decisions 호출·Jev 교체·판단 예산 배정은 하지 않았다.

## 실제 지원과 한계

[공식 Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions)에 따르면 `/v1/decisions`는 현재 공개 베타이며 gpt-6-luna만 지원한다. 질문별 predicate, choice, score와 확률을 반환한다. 표준 입력 100만 토큰당 USD0.10이며 이 엔드포인트에는 출력·캐시 비용이 없다. 일반 Responses 생성 요금과 구분해야 한다. 동일 OpenAI Bearer API 키 인증을 사용하지만, 첨부 키의 Decisions 엔드포인트 권한은 실제 호출로 확인하지 않았다. 모델 목록에서 gpt-6-luna 접근 표시만 확인했다.

confidence와 choice 분포는 별개다. Jev의 `.8`을 그대로 이식하면 같은 정확도를 보장하지 않는다. 공식 가이드도 자체 라벨 사례로 임계값을 정하도록 안내한다. 한국어, 인용 속 공격, 대상 구분, 칭찬 반복의 의미 구분 품질은 미검증이다. [Luna 모델](https://developers.openai.com/api/docs/models/gpt-6-luna)의 Responses structured JSON도 대안이지만 현재 판단의 범주·강도에는 전용 Decisions를 먼저 비교할 근거가 있다.

## 제품에 넣을 위치

| 방안 | 장점 | 판단 |
|---|---|---|
| Jev를 대체하는 사건 해석기 | target/act와 강도·관계 분류를 같은 입력에서 평가, 입력당 판단 서비스 하나 유지 | 우선 비교 후보. 감정 증가량은 기존 Core가 계산 |
| Jev 뒤에 별도 참여 모델 추가 | 애매한 듣기 요청·재접근 표현을 유연하게 해석할 수 있음 | 실제 오분류가 남을 때만 검토. 비용·지연·엇갈린 판단 증가 |
| 생성 모델이 감정·참여·숨김까지 결정 | 호출 수가 적어 보임 | 권하지 않음. 생성 실패와 의도적 침묵을 구분하기 어렵고 상태 경계를 무너뜨림 |

현재 `chooseSocial`이 명시적 듣기 요청·이유 재접근을 정규식으로 구분한다. 이 부위의 표현 범위가 좁다는 것은 코드 관찰이며 이번 API가 해결했다는 뜻은 아니다. 판단 모델은 입력의 대화 행위와 근거를 분류할 수 있다. 말할지·침묵할지의 최종 정책, 이유 저장, 공개 수준, 감정 지속·감쇠, 삭제 후 재계산은 Core/Store가 계속 소유한다. 주제 전환이나 다시 말을 건 사실만으로 불편함을 초기화하지 않는다.

## 추후 비교를 시작할 때의 최소 계약

1. 기존 `AppraisalProvider` 뒤에 후보를 연결하고, 해당 공급자의 결과와 현재 이벤트·revision을 확인하는 verifier를 함께 등록한다. Jev verifier로 새 결과를 신뢰하지 않는다. 키는 같은 비밀 파일에서 읽되 역할 설정과 총예산 원장은 구분한다. 이번 USD1은 생성 비교 한도이며 추가 승인으로 해석하지 않는다.
2. 현재 합성 판단 자료와 실패 사례를 고정해 target/act, 감정 근거, 듣기 요청, 침묵 이유 질문, 칭찬 의미 반복을 비교한다. 기존 자료는 dev로 표시하고 별도 미사용 확인 자료는 사전에 분리한다. 튜닝 후 같은 자료를 새 합격 증거로 쓰지 않는다.
3. 확신 부족·거절·사용량 불명·오류는 defer로 보낸다. 공급자 실패를 intentional silence나 새 침묵 이유로 저장하지 않는다. 한 이벤트의 감정 적용은 최대 한 번이다.
4. 인용·타인 공격을 캐릭터 공격으로 처리하는 오류0, 근거 없는 감정 변화0, 없는 침묵 이유 생성0, 실패의 의도적 침묵 포장0을 필수로 둔다. 듣기 요청·재접근·반복의 정확도와 지연·비용은 Jev 기준선과 함께 제시하고 임계값은 dev에서 정한 뒤 확인에서는 고정한다.
5. 기존 감정 증가0 응답, 의도적 숨김, 주제 전환 뒤 감정 지속, 같은 이벤트 중복·삭제·복구 회귀를 유지한 후보만 실제 경로에 넣는다. 모의 회귀와 실제 판단 품질·Stage·제작자 수용은 각각 기록한다.

직접 변경 대상은 후보 어댑터/verifier, `apps/runtime/src/providers.ts`, 역할별 config, 합성 평가기와 경계 검사다. 새 감정 축이나 DB 엔티티는 현재 근거로 필요하지 않다. 호출 전 최신 베타 계약·키 권한·가격과 별도 또는 공유 총예산을 다시 고정한다.
