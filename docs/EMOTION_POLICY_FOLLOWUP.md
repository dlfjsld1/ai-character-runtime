## 권장 순서와 성공 기준

### 1. 의미가 확실한 사건에 대한 작은 반응 정책

채택한 선택형 v4 정책은 **직접 칭찬 yes, 직접 공격 no가 검증됐을 때 작은 긍정 반응을 허용하고 큰 반응에만 강도 근거를 요구**한다. .95/.05의 사건 판정·출처 검증은 유지한다. 강도 하한이1 이상이면 기존 값을 그대로 쓰고, 하한0일 때만 strength1에 해당하는 작은 반응을 허용한다. 이를 강도 confidence 상승으로 기록하지 않는다. 듣기 요청·반복 제한·관계 호감·공격에 자동 확대하지 않는다. 선호 질문에 별도 답변을 받은 것은 아니며, 최대 진행 요청 범위에서 기본 공급자를 유지한 선택형 정책으로 구현했다.

대안은 intensity 질문을 사건이 있다는 조건 아래의 크기로 다시 설계하는 것이다. 실제 API 의미 비교가 필요하며, 현재 응답을 새 질문의 응답처럼 재사용하면 안 된다. 두 변경을 한 번에 넣어 원인을 혼합하지 않는다.

구현은 `packages/adapters/src/openai-interaction-v4.ts`의 별도 verifier와 provider/config 등록, `CHARACTER_DOMAIN_SPEC.md`의 감정 권한 설명에 반영했다. 기존 v3 원문을 새 권한으로 소급 재해석하지 않는다. Store의 관계 제외·원인 삭제·출처 바인딩과 Core의 반복/감쇠 공식은 유지했다. 관련 단위75건·DB19건 및 실제 판단1회의 범위와 최초 검사 오류는 연결된 결과 문서에 기록했다.

성공 기준:

1. P1형 확실한 칭찬에서 joy>0, 첫 자극≤.06. happy 표시를 필수로 요구하지 않는다.
2. 직접 공격이 yes/unknown, 칭찬이 no/unknown, 인용·타인·부정·가정인 경우 새 긍정 권한0. 잘못된 revision·context hash·실패 metadata는 권한0.
3. 듣기 요청은 감정 변화가 있어도 silent/listening, 일반 질문은 감정0이어도 응답 가능. 기존 한 번의 제한 수선과 숨김·기술적 보류를 유지한다.
4. 같은 칭찬 반복 시 기존 소비·감쇠·hold 규칙을 적용하고 관계 호감 추가0. 원인 삭제/복구 뒤 수치·참조가 기존 계약과 일치한다.
5. `openai-interaction*.test.ts`, `character-core/src/affect-evidence.test.ts`, `evals/affect-evidence.test.ts`, `evals/interaction.test.ts`에서 해당 경계를 검증한다. 기록 재생은 진단으로만 사용하고 새 한국어 정확도 통과로 합산하지 않는다.

### 2. 숨김의 자연 도달성

기존 이유 공개는 withholding에서 frustration≥.60이면 deflect,≥.20이면 partial, 그 아래면 explain이었다. 반복 공격의 자극 제한은 한 상대당 .24이므로, 낮은 빈도의 일대일 대화에서 .60을 기준으로만 숨김을 선택하는 것은 제품 의도와 맞지 않을 수 있다. 후속으로 아래의 전달된 설명·현재 원인 조건을 구현했으며 기존 높은 감정 경로도 유지한다.

**감정 상한을 키워 숨김을 강제로 만들지 않는다.** 현재 불편함·유효한 같은 상대의 침묵/원인·최근 전달 기록을 함께 사용하는 아래 정책을 적용했다. 자동 수선·기억 없음·이유 창작으로 처리하지 않는다. 첫 설명까지 전부 회피하는 변경은 하지 않았다. 실제 공급자 선택과 한국어 숨김 표현 품질은 별도 검증한다.

관련 owner는 `character-core/src/index.ts::chooseSocial`, Store의 `previousSilence`/출처 재검증, `CHARACTER_DOMAIN_SPEC.md` §10.1이다. 기존 자료만으로 새 숫자 문턱을 임의 확정하지 않는다. 성공 기준은 상태 주입 없이 한 상대의 고정 대화에서 의도한 공개 수준에 도달하고, 별도 설명 필수/기록 없음/삭제/주제 전환 사례는 원래 동작을 유지하는 것이다.

2026-10-15 구현한 정책은 **이미 전달한 같은 이유의 반복 질문에서 공개를 줄이는 정책**이다. 불편함 공개 구간은 .20에서 진입하고, 같은 유효 침묵 기록이 .20 이상을 보존하며 연결된 현재 원인이 있을 때 .10 미만까지 유지한다. 이는 기존 표정의 진입/해제 간격을 공개 선택에도 적용하되 표시 표정 자체에 의존하지 않는 정책이다. 현재 유효한 withholding 사건 또는 기록에 연결된 같은 상대의 출처가 감정 원인에 남아 있고 같은 사건을 explain/partial로 전달 완료한 응답이 검증된 최근4교환에 있고 이 구간이 유지될 때만 새 deflect 경로를 허용한다. 현재 사과·대상 정정이 포함된 질문에는 새 경로를 적용하지 않는다. 첫 설명과 listening/no_addition·기록 없음·출력 실패의 동작, 기존 .60 이상 deflect 경로는 유지한다. 이는 반복 질문을 공격으로 판정하는 규칙이 아니라 캐릭터의 공개 선택이다.

Store는 기존 conversation의 완료된 assistant response 참조와 plan을 읽어 근거를 확인한다. 대사 문구를 분석해 ‘설명했음’을 추측하거나 새 테이블·장기 marker를 만들지 않는다. Core에는 확인한 silence event ID와 출처 검증을 마친 침묵 기록을 전달한다. 새 기록은 남아 있는 같은 상대의 frustration 원인도 sourceRefs에 결합한다. 감정 증가량0인 최신 사건 자체를 새 감정 원인으로 만들지는 않는다. 정정/삭제·미전달/실패·다른 상대/다른 이유·최근 문맥 밖 응답은 근거가 아니며 기존 response/context 무효화 경계를 따른다. 주제 전환은 최근 문맥에 설명이 남아 있으면 근거를 지우지 않는다.

성공 기준은 상태 주입 없이 공격2→첫 이유 설명(partial) 완료→주제 전환→같은 이유 질문(deflect)이다. 사과 동반 질문은 새 회피에서 제외하고, 이유 출처/이전 설명 삭제·미전달·다른 이유·문맥 이탈·감정 원인 불일치에서는 새 권한0이어야 한다. 입력 전후 감정은 기존 시간 감쇠만 적용되고, 공개 선택 자체가 감정을 올리거나 완화하지 않아야 한다. 구현 파일은 `character-core/src/index.ts`, `database/src/store.ts`와 해당 Core/DB 검사이며 공급자 질문·모델·wire·DB schema는 바꾸지 않는다.

### 3. 표현 평가 문항과 표시 증거

세 상태에 동일하게 사용할 질문 후보: “모임은 오후3시야. 준비를 같이 시작하자. 시간도 짧게 확인해 줘.” 시간 사실 하나와 호응의 여지를 함께 둔다. 단순 “몇 시야?” 문항은 사실 보존 회귀로 유지하되 감정 말투 차이의 유일한 근거로 쓰지 않는다.

내부 상태 도달, 표현 Plan, 한국어 생성, 실제 Stage 전달, 사람의 체감 수용을 각각 기록한다. 감정 표현 차이는 사실·문장 제한을 지킨 문장 쌍을 제작자가 비교한다. 의도적 숨김으로 사전 선택된 경우만 차이가 작을 수 있고, 실패 후 숨김이라고 설명하지 않는다.

`evals/browser/caption.ts`를 만들고 B2 도구와 기존 브라우저 검사가 같이 사용하도록 수정했다. 캡처 전후 DOM에 같은 비어 있지 않은 자막이 있어야 하며, B2에서는 첫 speech segment와도 일치해야 한다. 새 함수는 합성 Chrome1건으로 검증했다. 과거 B2의 빈 캡처는 그대로 보존하며 이 수정으로 과거 사진 증거가 생긴 것은 아니다.

### 4. 비용과 실행 범위

`DialogueBudget.summary()`와 `scripts/diagnose.ts`는 실제 청구 미확인(`billingVerified:false`), 모델 사용량 추정, 계수 예약, 미확인 모델 예약, 차단용 합계·잔여액을 분리한다. 원장 쓰기·API 호출 없이 동작하고, 잠금/손상은 unavailable로 표시한다. 기본 차단과 기존 unknown·횟수 한도는 그대로다.

신규 회귀2건은 수정 전 실패했고 수정 후 관련31건·타입 검사 통과. 실제 진단에서 원장 해시가 동일했다. 증거는 `runtime-baseline-20261015/budget-summary-{red,green,diagnostic}.json`이다. 다음 실제 실행 전에는 정책·고정 문항·횟수와 금액 경계를 함께 확정한다. 낮은 플랫폼 청구 보고를 임의 원장 초기화 근거로 쓰지 않는다.

후속으로 준비 단계와 생성 직전의 동일한 전체 요청 계수를 한 번만 수행하도록 수정했다. 요청이 다르면 재계수하고 생성 예산·실제 usage 검사는 유지한다. 관련 단위113·DB/Coordinator21·타입 검사를 통과했으며 추가 실제 호출은0이다. [검증과 최초 기대 오류](./EMOTION_RUNTIME_RESULT.md#prepared-count-reuse)를 따른다. 계수 무료 여부나 실제 청구 정산은 여전히 미확인이므로 이 최적화가 과거 예약을 해제하지는 않는다.

이 단락은 최초 후속 실행 당시 기록이다. 현재 기술 검증·통제 표현 대조 결과는 위 현재 상태와 [표현 대조 결과](./EXPRESSION_CONTRAST_RESULT.md)를 따른다. 당시 통과한 기술 경로와 미통과한 감정 체험을 구분한다. G3-L 프로세스 재시작 대조는 후속 실제 브라우저/합성 공급자 실행에서 통과했다. 작은 긍정 반응안은 선택형 v4로 구현됐고, 자연 숨김·감정 표현 대조·G3-S 전체와 G3-U 제작자 수용은 남아 있다.
