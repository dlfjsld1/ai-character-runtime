## 준비한 요청의 계수 재사용 — 2026-10-15 후속

공식 [계수 안내](https://developers.openai.com/api/docs/guides/token-counting)에서 입력 메시지·스키마 등을 포함한 계수 방식을 다시 확인했다. 해당 안내와 [가격표](https://developers.openai.com/api/docs/pricing)에서 계수 요청의 무료 여부는 확정하지 못했다. 따라서 과거 예약을 무료로 정산하거나 원장 합계를 낮추지 않았다.

`OpenAIDialogue.fitConversation`이 검증한 최종 요청을 `dialogue`가 그대로 보낼 때만 계수 결과를 한 번 재사용한다. 전체 요청 JSON이 바뀌거나 중간에 다른 공급자 호출이 있으면 다시 계수한다. 새 fit과 소비 시 이전 준비 기록을 지우며 파일에는 저장하지 않는다. 생성 요청 자체의 예산/횟수/unknown/lock 검사는 계속 실행하고, 실제 usage가 준비된 입력 계수와 다르면 대사를 노출하지 않는다. 대화 이력768·전체3328·출력256 제한과 포트는 유지했다.

수정 전 집중 검사23개 통과/3개 실패로 중복 계수를 재현했다. 수정 후 adapter·예산 관련 단위113개, DB·Coordinator21개와 타입 검사를 통과했다. DB 경로는 정상 registry의 v4와 OpenAI 생성 adapter를 쓰되 네트워크 응답은 합성했다. 이력 계수1·전체 요청 계수1·생성1로 저장된 자막과 전송/ACK 완료를 확인했다. 실제 Chrome 렌더링이나 모델 자연스러움 검사로 계산하지 않는다. DB 첫 실행의 새 검사1개는 기존 인사 이력의 필요한 계수까지 중복으로 센 기대 오류였으며, 전체 요청의 중복만 구분해 수정했다. 최초 결과는 보존했다.

증거는 `${ARTIFACT_ROOT}/runtime-baseline-20261015/prepared-count-{red,green,integration,integration-final}.json`이다. 실제 API 호출0, 과거 원장 변경0. 기존 보수 예약과 소진된 역할별 횟수 한도가 해제된 것은 아니다. 다음 실제 G3-S16에는 같은 원장의 금액·누적 횟수 범위를 먼저 정해야 한다.
